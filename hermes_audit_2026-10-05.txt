[5] BACKUPS FAIL ON A FRESH DEPLOY (verified live, then fixed
    live to confirm root cause).
    Symptom: POST /api/backups/run -> 202, then history shows
      status=Failed, "Cannot open backup device '/var/backups/....bak'.
       Operating system error 5(Access is denied.)".
    Root cause: the shared volume `sqlserver_backups` is created
    root:root 755; SQL Server runs as uid 10001(mssql) and cannot
    write into it. The daily 02:00 UTC job will fail the same way
    on every fresh machine -> module 7's "automated backups" claim
    is broken AND the public status page shows "Degraded"
    (backup-freshness) forever.
    VERIFIED FIX: after `docker exec -u 0 hrmsystem.sqlserver
    chown 10001:10001 /var/backups`, the backup succeeds (2.4 MB
    compressed .bak, history=Succeeded, status page flips Healthy).
    Make it permanent for new machines - add a tiny init service:
      hrmsystem.backup-perms:
        image: alpine:3
        volumes: [ sqlserver_backups:/var/backups ]
        command: sh -c "chown 10001:10001 /var/backups"
    and make sqlserver + api depend_on it with
    condition: service_completed_successfully.
    EVAL-DAY TIP: after starting the stack, log in as host-admin and
    POST /api/backups/run once, so the status page shows Healthy
    during the demo instead of "Degraded" (no backup yet).

[6] SIGNALR WEBSOCKETS BROKEN -> CONSOLE ERRORS ON EVERY PAGE.
    (This is your July [17] "Firefox WebSocket issue" - it is NOT
    Firefox-specific; I reproduced it in Chrome/154 and fixed it.)
    Symptom: every route logs, in a real Chrome console:
      "WebSocket connection to 'wss://localhost:5100/hubs/...
       failed: HTTP Authentication failed; no valid credentials"
      + warning "MONO_WASM: WebSocket error".
    Root cause: browsers cannot send an Authorization header on the
    WS handshake, so the SignalR JS client puts the JWT in
    ?access_token=... . The server-side handler that reads it
    (JwtBearerOptionsSetup.OnMessageReceived, which exists and is
    correct) is NEVER REGISTERED - no
    services.ConfigureOptions<JwtBearerOptionsSetup>() anywhere in
    DI. So all WS handshakes get 401, SignalR falls back to
    long-polling (works, but slower) and the console shows errors.
    That breaks TWO things: the mandatory "no errors/warnings in
    the browser console" requirement, and the credibility of the
    real-time module demo.
    VERIFIED FIX - one line in
    src/Infrastructure/HrmSystem.Infrastructure/DependencyInjection.cs
    right after the .AddJwtBearer(...) block:
        services.ConfigureOptions<JwtBearerOptionsSetup>();
    After this: negotiate+WS handshake -> 101 Switching Protocols
    (27 upgrade 101s logged), console sweep over all 15 routes:
    0 errors / 0 warnings. Rebuild api image and re-test.
